# 独立程序统一任务接口与协作约定

本文供 Codex、ZCode 和后续接手开发者使用：先约定模块调用、任务结果和失败处理，再实现独立程序。用户在 2026-10-05 指定 Codex 负责操作与兜底机制，ZCode 负责主程序接线、模块调用与联调。

**状态：v1 核心和主程序接线已实现，已做离线端到端与故障验证。** 2026-10-05 用户再次授权补齐并要求 AI 自动审核、电脑长期运行。真实模型质量、真实采集、Notion、正式库链路及连续 24 小时仍未验收；本轮不启动这些真实调用或打包发布。

## 1. 范围与原则

- 在现有 Python 服务外加薄的任务编排层，复用 GraphService、InboxWatcher、NoteProcessor、DiscoveryService、NotionSyncCore，不整体重写，也不新增第二套图谱或知识数据库。
- 任务账本只记录运行进度、产物引用、校验和与恢复信息，不承载第二份权威知识节点。知识与 Skill 仍在授权的 Obsidian 库；状态由现有受控服务管理。
- 程序固定执行和安全边界；领域认知、知识增量、笔记表达继续由 Skill 与模型处理，不硬编码成各领域的 Python 模板。
- 一次提交一个文件或一个链接；完整处理单份材料，不默认截取前 5000 字符，不设置统一的文件大小/全文长度拒绝上限。传输、分段、并发与重试需要资源控制，但不得静默截断正文。
- 既有笔记未经逐项授权不得修改、覆盖、追加、移动、重命名或删除；默认仅新增候选材料。已有授权的自动收录配置应显式读取并展示，不能从“模型说成功”推导出授权。生成、收录、用户阅读、测验通过是不同事实。
- 镜像默认关闭；Notion 发布是独立且显式授权的动作，不是必经步骤。
- 保留现有 Web/Tkinter 功能；先适配调用，再按必要性整理文件。优先便携目录版，不先引入微服务或新的 Agent 编排框架。

## 3. 最小调用接口

类名固定为 `WorkflowService`，模块为 `pka_graph/workflow.py`。对接者调用公共方法，不直接改任务账本。

```python
WorkflowService(
    store: TaskStore,
    *,
    adapters: Mapping[str, StageAdapter],
    pipelines: Mapping[str, tuple[str, ...]],
    authorize: Callable[[Principal, str, dict], None],
)

submit(request: dict, *, principal: Principal) -> dict
get(task_id: str, *, principal: Principal) -> dict
cancel(task_id: str, *, request_id: str, principal: Principal) -> dict
retry(task_id: str, *, request_id: str, principal: Principal) -> dict
capabilities(*, principal: Principal) -> dict
```

`Principal` 由服务端认证构造，含调用者身份、可用动作和授权范围；不得接受客户端 JSON 中自报的权限。恢复与工作线程启停是服务内方法，不开放成任意 Agent 可执行的修复接口。

内部生命周期固定为 `start() -> None`、`stop(*, timeout: float = 5.0) -> dict`、`recover() -> dict`；启动先核实恢复记录，再消费可运行任务。stop 返回仍未停止/结果未知的任务 ID，不能超时后宣称全部退出。ZCode 在服务构建时注入适配器，在启动/退出时调用生命周期方法；不在 import 时启动线程。

`adapters` 的键固定为阶段名（如 `extract`），值为一个 `StageAdapter`；`pipelines` 的键为请求中的流水线名，值为阶段名有序元组。适配器可以根据已校验的 source.kind 在已登记工具间分流，不从客户端加载 Python 类。ZCode 在 `build_service()` 中构造一次并挂到 `svc.workflow`，核心模块不反向导入适配器文件。

`TaskStore` 从 `pka_graph.task_store` 导入，构造为 `TaskStore(state_dir: Path)`，state_dir 固定为 `<vault>/个人学习状态/tasks/_ledger/`，与各 task_id 目录同级。其底层格式为内部实现，调用方不直接读写。`WorkflowService`、`Principal`、`StageContext`、`StageResult`、`StageAdapter`、`WorkflowError` 统一从 `pka_graph.workflow` 导入。

`Principal` 为冻结数据对象：`subject: str`、`scopes: frozenset[str]`。最小 scope 名称固定为 `tasks:submit`、`tasks:read:self`、`tasks:control:self`、`tasks:admin`、`publish:notion`；任务保存 owner，默认只能读/取消/重试自己任务。路径、目标和外发权限由服务端 `authorize` 回调按当前配置复核，失败抛出受控权限错误。提交时的授权快照不能替代执行/提交时的再次授权。

权限映射：经可信启动流程认证的本地主人会话拥有 submit/read:self/control:self/admin；Notion 仍要求目标授权。已有 `PKA_EXT_TOKEN` 只维持旧 `/api/ext/*` 的只读能力，不因新路由获得 submit/control/publish。新 Agent 写入凭据须由服务端显式配置其身份与范围。公开 `/` 自动发一枚全权限 cookie 不能代替身份认证；移除 meta 明文令牌时，应通过启动器提供的一次性票据交换 HttpOnly/SameSite=Strict 会话，并保留桌面入口的受控认证通道，不能让匿名本地请求自动升级管理员。

认证接线接口固定为 `POST /api/session/exchange`，body 为 `{"ticket": "..."}`；成功返回 `{"session_token": "...", "expires_at": "UTC ISO-8601", "scopes": [...]}`，并设置 `pka_session` HttpOnly/SameSite=Strict cookie。桌面使用 `X-PKA-Session`，浏览器使用 cookie；Host/Origin/JSON 校验继续生效。两者的主人 subject 均为 `local:owner`，避免互相看不见任务。

票据由可信主程序启动器生成，单次消费、60 秒有效；浏览器使用 URL **fragment** `#ticket=...` 并在交换后移除，禁止放 query 进入访问日志。桌面由主程序经子进程环境/受控 IPC 交付独立票据；浏览器与桌面不能争抢同一张票。不提供匿名取票端点，不在公共配置文件中落盘管理员密钥。未经主程序启动的独立客户端提示重新从主程序连接，不能退回读取 meta 令牌。重放/非法票据 403，过期 410。移除 meta 令牌、浏览器与桌面的引导更新必须同批交付。

此认证限制程序接口调用，不是对同一 Windows 用户下任意高权限编码 Agent 的操作系统隔离；若 Agent 本来能读取整个用户目录/进程环境，需要另外收紧它自身权限。

### 提交数据

```json
{
  "contract_version": 1,
  "request_id": "调用方生成的唯一请求标识",
  "source": {"kind": "file", "path": "授权输入目录内的单个文件"},
  "options": {"pipeline": "note", "publish_to": null}
}
```

- `source.kind` 第一版为 `file` 或 `url`；URL 只交由已经登记的来源适配器处理，不提供任意网页自动操作或任意命令入口。
- `pipeline` 第一版为 `note`（已有资料加工）或 `transcribe_then_note`（视频/抖音取得文稿后加工）。未实现或缺依赖的能力明确返回 `not_supported`，不伪装成功。
- `publish_to` 只接受服务端配置中的目标别名，默认 `null`；不能提交任意 Notion 父页面、任意文件写入位置或任意模型地址。
- 现有 `/api/inbox/ingest` 上传继续兼容。文件较大时采用流式/分块传输，不能把“base64 JSON 全装进内存”当作无限单文件支持。上传完成且服务端确认落地后，再进入同一提交接口。
- 输入首先冻结到任务自有工作区并计算 SHA-256；后续提取、模型处理、校验使用这一版本，不重复读取不断变化的用户原文件。

### 任务数据布局

工作区固定为 `<vault>/个人学习状态/tasks/<task_id>/input/`、`work/`、`output/`；Codex 核心创建并记录归属。input 放冻结原件，work 放可恢复分段，output 放已生成但未正式发布的成果。一次任务只冻结一个原始文件；其转写/提取结果是派生产物，不算第二份输入。

`outputs[].path` 和 artifacts 中的 path 统一为**相对 vault 根目录**的路径，使用 `/` 分隔，客户端结合已授权 vault 根路径显示；不得放绝对路径或 `..`。工作进程用 `context.work_dir`（绝对 Path）操作自己的文件。解析路径须 resolve 并检查根目录，不把拼接字符串视为安全检查。输入快照创建属于核心 acquire，ZCode 的 acquire 适配器只处理有明确授权的下载等来源准备工作，不重复冻结/登记任务。

清理只由核心按自身记录与指纹执行；人工改动、归属不明、仍在运行的任务目录不能删除。第一版不自动清理成功产物或用户原文件，不整目录搬动已有知识库。

### HTTP 映射（由 ZCode 接线）

| 路由 | 公共方法 | 结果 |
| --- | --- | --- |
| `POST /api/tasks` | `submit` | 登记后返回 202 和任务快照，不在请求线程里跑完整模型链路 |
| `GET /api/tasks/{task_id}` | `get` | 200，统一快照 |
| `POST /api/tasks/{task_id}/cancel` | `cancel` | 200，记录取消请求；不假称远端请求已被撤回 |
| `POST /api/tasks/{task_id}/retry` | `retry` | 202，原任务增加 attempt，复用已核验产物 |
| `GET /api/tasks/capabilities` | `capabilities` | 200，列出已实现/已配置/可用能力与缺失原因，不只列函数名 |

鉴权沿用本地服务，但不得把管理写令牌通过未鉴权 `/api/meta` 提供给所有客户端；读、投递、取消/重试本人任务、发布分别授权。旧读接口不因此获得写权限。

调用级错误由 `WorkflowError(code, message, *, http_status=400)` 表达，提供 `as_dict() -> dict` 返回 `{"error": {"code": str, "message": str}}`，由 HTTP 层统一转换。参数非法 400、未认证 401、无权限 403、不可见/不存在的任务 404、幂等冲突或不可执行的状态转换 409；不要返回异常堆栈。任务已登记后发生的阶段错误写入快照中的 error，通过 GET 正常返回 200，不把业务失败伪装成 HTTP 服务断开。

capabilities 返回固定为 `{"contract_version": 1, "pipeline_mode": "legacy|task", "capabilities": [{"name": "note", "implemented": false, "configured": false, "available": false, "reason": "..."}]}`；`transcribe_then_note`、Notion 等逐项报告，缺外部转写 worker 时必须不可用。v1 暂不新增任务列表路由，沿用 registry 兼容视图加单任务查询。

## 4. 统一任务快照与身份

所有入口返回相同字段；CLI/桌面/HTTP 不各自编造成功含义。

```json
{
  "contract_version": 1,
  "task_id": "服务生成的 UUID",
  "request_id": "首次提交标识",
  "attempt": 1,
  "status": "running",
  "stage": "generate",
  "stages": [
    {"name": "acquire", "status": "completed"},
    {"name": "extract", "status": "completed"},
    {"name": "analyze", "status": "completed"},
    {"name": "generate", "status": "running"}
  ],
  "progress": {"completed_units": 2, "total_units": 5},
  "outputs": [{"kind": "source_text", "path": "任务产物路径", "sha256": "...", "complete": true}],
  "result": null,
  "error": null,
  "cancel_requested": false,
  "next_retry_at": null,
  "created_at": "UTC ISO-8601",
  "updated_at": "UTC ISO-8601"
}
```

- `task_id` 为唯一 UUID；`request_id` 是调用幂等，不是任务 ID；`attempt` 为尝试次数。不用“内容前缀+秒数”当唯一任务 ID。
- 幂等作用域为 `(owner, request_id)`，不同身份不能串任务；重放同一键返回同一任务，请求参数、目标或输入版本发生变化时返回冲突。`contract_version != 1` 返回 400 / `contract_version_unsupported`，不入队。
- 成果去重键由冻结原文哈希、流水线、Skill 内容哈希、模型/配置指纹、目标范围构成；密钥不参与持久化指纹。相同内容发往不同目标，不共用远端进度。
- `progress` 只表达可测量的已完成单元；未知总量为 `null`，不能编造百分比。`outputs` 只暴露当前调用者有权读取的产物路径，不返回完整正文或密钥。
- `stages` 按流水线顺序返回所有阶段，未执行为 `pending`、不适用为 `skipped` 并带 reason；已完成为 `completed`。失败、阻塞、未知、取消或等待重试沿用任务状态名。阶段记录保留 attempt、错误和产物引用，主程序据此展示“笔记成功，发布失败”。
- 语义判定另放结果中：候选、已收录、已同步、untested/passed 不能用一个 `status` 混在一起。任务 succeeded 不代表用户掌握。
- `result` 为 `null` 或对象，固定可选字段为 `suggestion_id`、`note_status`、`node_id`、`notion_page_id`、`disposition`；disposition 可为 `candidate/collected/duplicate/insufficient/news_only`。不再产生独立第二套掌握状态。
- `result.verdict` 原样保留现有发现分类。duplicate/insufficient/news_only 同名映射 disposition；等待审核的 new_node/supplement/revision 为 candidate；完成授权的新建或更新建议登记为 collected（不等于已更新原笔记）。不得仅因 verdict=new_node 就标 collected。

## 5. 状态机与结果边界

状态固定为：`queued`、`running`、`retry_wait`、`blocked`、`needs_review`、`unknown_result`、`succeeded`、`failed`、`cancelled`。

- 正常路径：`queued -> running -> succeeded`。
- 可自动重试的失败：`running -> retry_wait -> running`；同一阶段最多 3 次总尝试（首次+2 次重试），达到上限变 `failed`。全文加工无调用总额上限，不等于失败无限重试。
- 缺配置/认证/必要来源/能力：`blocked`，不消耗模型循环重试；修复后显式 `retry`。
- 笔记未达内容门槛、需用户确认的收录：`needs_review`；不可冒充正式提交成功。
- 外部写请求结果无法确认：`unknown_result`；禁止自动重发，先用明确的文档/版本身份核实。不能用同名标题认领用户旧页面。
- `cancel` 设置取消标识；阶段开始、每次网络/分段调用前及每次本地提交前检查。已明确取消的任务不可写入后续产物；正在远端写入的请求仍可能成功，核实不了时保留 `unknown_result`。
- `succeeded` 不可再重试；`running` 不可并发重试；`unknown_result` 必须先完成核实；取消任务重新执行需显式 retry，增加 attempt，不抹除旧记录。
- 系统内部恢复不等于用户重试：检查原文/产物/Skill/模型版本，恢复被中断任务；没有可靠检查点则标记需确认，不声称恢复成功。

阶段固定为：`acquire -> extract -> analyze -> generate -> validate -> commit -> sync`。按流水线可显式跳过不适用阶段，并记录原因；不是所有任务都做远端采集、ASR 或 Notion。

映射固定：generate 调 prepare_note，validate 调 validate_prepared，commit 调 commit_prepared，sync 调统一 Notion 核心。note 的 extract 负责文档正文提取；transcribe_then_note 的 extract 负责字幕/ASR，后续同一链路。publish_to=null 时 sync 标记 skipped。缺模型不是“不适用”，需要模型的阶段应 blocked，不能 skipped 后假装完成语义判断。

若笔记完成但 Notion 失败：保留笔记与提交记录，只重试 `sync`。如果外部写入已开始，超时不能回退成“什么都没发生”。

## 6. 阶段适配接口

ZCode 实现已登记的适配器，Codex 的调度层仅调用下列协议，不导入转写工具的隐式上传/移动副作用：

```python
class StageAdapter:
    def execute(self, context: StageContext) -> StageResult: ...
```

`StageContext` 由调度器创建，适配器只读使用：`task_id: str`、`attempt: int`、`stage: str`、已校验的 `source: dict`/`options: dict`、`work_dir: Path`、上游 `artifacts: tuple[dict, ...]`。方法固定为 `cancel_requested() -> bool`、`load_checkpoint() -> dict | None`、`save_checkpoint(data: dict) -> None`、`report_progress(completed_units: int, total_units: int | None = None) -> None`。保存与恢复的检查点必须属于当前任务/阶段及冻结版本。具体类型由 Codex 在 `workflow.py` 实现，ZCode 不另造第二份。

`StageResult` 为冻结数据对象，构造参数：`outcome: str`（必填，仅 `completed/blocked/needs_review/unknown_result/failed/cancelled`）、`artifacts: tuple[dict, ...] = ()`、`checkpoint: dict | None = None`、`error: dict | None = None`、`result: dict | None = None`。构造/校验失败是适配器错误，不能默默转为 completed。可预期业务错误返回 StageResult；未预期异常由核心捕获为脱敏 internal_error，不能自动无限重试。产物必须有来源版本和完整性信息，文件存在不足以证明成功。

副作用通过 `context.run_effect(effect_id: str, *, kind: str, action: Callable[[], dict]) -> dict` 执行；kind 仅为 `local_commit` 或 `remote_write`。这是可信适配器的内部 Python 调用，客户端不可提交 action。调度器先持久化意图并核验当前授权与取消标识；本地提交与 cancel 共用任务锁，锁覆盖检查到实际提交。远端请求先在锁内登记 in-flight 再发出，不持锁等网络；取消不保证撤销已发送请求，返回未知时优先保留 `unknown_result`。适配器不得绕过这个入口做发布/入库副作用。

effect_id 在同一任务及同一产物版本内稳定，跨 attempt 复用，不包含尝试次数；同 ID 但目标/产物指纹不同必须冲突。已确认提交直接返回保存结果；远端 in-flight 未核实时禁止再次执行 action。

适配器不直接推进任务状态，也不改任务账本；只有调度层推进。每阶段先登记意图，再执行可能的副作用；副作用提交记录、任务进度都持久化后才关闭意图。

第一版一次运行一个全文加工/ASR 任务，模型不参与编排或执行 Shell。保持简单，不先实现任意 DAG、动态插件市场或多 Agent 自治。

### 旧链路切换的必要约束

现有 `DiscoveryService.accept()` 同时做 NoteProcessor.process 和知识库提交。采用分离方案（ZCode 评审选项 b），由 Codex 认领 `discovery.py` 的最小拆分。**不把整个 accept 当成 commit 阶段重新跑模型。** 准备接口固定为：

```python
prepare_note(suggestion_id: str, *, context: StageContext) -> dict
validate_prepared(prepared_ref: str, *, context: StageContext) -> dict
commit_prepared(prepared_ref: str, *, context: StageContext,
                request_id: str, strict: bool = True) -> dict
```

prepare_note 返回 `{"prepared_ref": str, "artifacts": list[dict]}`；validate_prepared 返回 `{"publishable": bool, "reason": str, "admission": dict}`；commit_prepared 返回既有入库结果并明确 `published` 与 `deferred`。prepared_ref 是服务端任务内登记的引用，绑定任务/原文/建议/配置版本及产物指纹，既不是任意文件路径，也不接受客户端提供的模型正文。校验未通过时不能 commit。入库操作经 context.run_effect 执行；沿用并修复已有 discovery 意图日志，任务账本只引用 effect_id/intent_id，不再另造一套业务写入恢复。

`accept()` 旧入口暂时保留签名；新编排启用后，其授权动作应关联现有 task/prepared_ref，不能在另一线程重复调用模型。`needs_review` 经原人工接受入口继续原任务，准备结果变化或授权变化则重新校验。具体 wrapper 由 Codex 提供，ZCode 不复制 accept 实现。

锁窗口：下载、ASR、模型及 Notion 网络等待均不持 `material_lock`/状态写锁。prepare 取短快照后释放；commit 再取最新状态核验。固定锁顺序为任务提交锁 → `material_lock` → StateStore 事务锁，禁止反向获取。旧 Inbox 扫描不得持 material_lock 等待任务完成。

新编排启用时，Inbox 的上传与目录扫描只负责登记同一任务，不再自行 quick_scan 后另起一条 auto_accept 链；旧 registry 可由任务快照派生兼容视图。一个输入只能有一个调度所有者。未完成切换的旧入口要明确标记 legacy，不能混入新链路验收。

旧 `/api/inbox/registry` 和 `/api/inbox/status` 保留原字段，registry 新增 task_id；旧 `suggested` 只表示已有建议，不能映射成完整任务 succeeded。桌面逐步改为读统一快照，迁移期间仅派生兼容视图，不允许双方分别推进状态。`capabilities` 路由先于动态 task_id 路由匹配。

切换开关固定为 `PKA_TASK_PIPELINE=legacy|task`，迁移开发期默认 legacy，明确出现在 capabilities；新的接口能力不能在 legacy 模式冒称已接入。task 模式下所有来源都交给同一调度器；legacy 模式下旧上传响应保持原样，task 模式保留 queued/status 并增加 task_id。上传只原子落地，提交只接收已落地单文件路径。旧桌面 20MB 属当前传输限制，需随流式/分块上传一起解除，不得宣称当前已完整支持任意单文件。

Quiz 保留独立会话状态机，本轮不塞入材料处理任务，也不改变掌握判定权限。

## 7. 错误、写入与恢复契约

错误对象固定字段：`code`、`stage`、`message`、`retryable`、`requires_confirmation`。面向用户的 message 使用中文并脱敏，不回显模型请求、HTTP 错误正文、密钥或私人问答。

| 错误 | 默认处理 |
| --- | --- |
| `auth_error/config_error` | blocked，修配置后重试，不自动烧预算 |
| `source_changed/source_missing/not_supported` | blocked，保留产物与原因，不静默补造材料 |
| `network_error/rate_limited` | 有限退避；只有确定无副作用的请求才自动重试 |
| `context_exceeded` | 保留完整正文，进一步分段/分层合成；不截取、不无限发同一请求 |
| `invalid_output/incomplete_output` | 保留候选与诊断，不正式发布；有限修复失败后 needs_review |
| `write_conflict` | 在写事务内重验最新版本；超过有限次数停止，不覆盖人工变化 |
| `ledger_corrupt/state_corrupt` | blocked，保留损坏原件，绝不读成空状态继续覆盖 |
| `remote_result_unknown` | unknown_result，不自动创建/追加或重跑整链 |
| `permission_denied` | 明确拒绝，不尝试换路径、换账号或绕过权限 |

任务账本与权威状态分别进行事务保护；每个知识库只允许一个服务写入者。唯一临时文件名+原子替换仅解决半文件，还需要锁住检查版本到提交的全过程。

运行锁/租约使用一致时间基准、唯一 owner、心跳与条件释放。Windows 禁止用 `os.kill(pid, 0)` 探测存活；探测失败不等于可以接管。旧持有者不得释放新持有者的锁。

模型分段检查点按原文哈希+Skill 内容哈希+模型配置绑定，恢复时验证，已完成段落不重算。最终合成也要受上下文约束，不能分段后又把全部原文塞回一个超限请求。

Notion 认领仅依据已持久化的 page_id/文档版本归属，或在明确授权的新建目标范围内可核验的完整身份标记。同标题不是授权，也不能先读取任意同名私人页面正文来猜测身份。首轮无法可靠核实时保留 unknown_result 交人工处理；不以“自动恢复”名义放宽读取/追加范围。

只清理任务自己创建且可验证归属的临时文件；用户原件和人工修改文件绝不删除。发布与回退按精确对象清单处理，不递归删除知识库或用户目录。

## 8. 第一轮开发和验收

1. Codex 先做核心安全修复与上述协议/任务状态机；ZCode 同时只做其认领文件的适配和路由，使用相同假适配器。
2. ZCode 负责离线主程序集成：旧入口仍能调用；新提交返回任务 ID；进度事件不丢失；状态失败与产物成功分别可见；程序关闭正确通知任务。
3. 双方交叉检查：先验证双方文件差异，再跑契约与故障注入测试；不以绿色测试数量代替真实能力验收。
4. 稳定后再做便携包检查；当前 `packaging/` 是已有用户工作，不能在未协调前覆盖。发布资源、模型与用户知识库/密钥/任务数据分开，更新程序不覆盖用户数据。

必须覆盖的离线用例：同 request 重放；同秒不同目标不碰撞；两个状态写入不丢更新；取消后不迟到提交；第二阶段失败不重跑第一阶段；认证错误不循环重试；账本损坏停止写；远端未知不重复创建；中断后恢复已完成分段；原文件等长修改不混用版本；同名笔记不覆盖；UI 不丢任务事件；定时检查真正执行；未实现能力如实返回不可用。

接线验收补充：票据重放/过期拒绝；未认证新任务路由 401；只读 ext 身份无写权限；两种模式都只有一个执行所有者；缺模型不当作成功跳过；浏览器和桌面能看到同一主人任务；取消发生在提交前后分别保留真实结果。

真实模型质量、真实抖音采集、真实 Notion 和正式知识库链路须另行取得授权后验收。本轮接口协商不能写成“全链路已接通”。
